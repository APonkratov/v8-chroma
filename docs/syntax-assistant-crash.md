# Сбой синтаксис-помощника: уничтожение HTML-окна

## Установленные факты

Пользователь сообщил о закрытии 1С 8.3.27.2325 x64 после открытия СП,
ввода `ПланОбмена` в индексе и одного или двух Enter. В процессе была подключена
раскраска v8-chroma 0.4.0. Логи этого процесса подтверждают One Dark Pro,
новые значки и восемь цветовых перехватов WebKit. Был запрошен JetBrains Mono
Medium 10 pt; обновление редактора завершилось `ERROR_NOT_READY`. Движок шрифта
интерфейса был загружен, но успешное применение в его сессии не зафиксировано.

В дампах от 29 октября и 2 ноября 2026 года совпадают адрес и цепочка сбоя:

```text
WebKit.dll+0x260A5A  AXObjectCache::rootObject(), this == nullptr
WebKit.dll+0x0B8E60  конструктор обёртки доступности документа
WebKit.dll+0x0DC7F4  получение доступного объекта WebFrame
WebKit.dll+0x10E4DF  обработка WM_GETOBJECT / OBJID_CLIENT
WebKit.dll+0x110E58  оконная процедура WebView
... UIAutomationCore / oleacc ...
WebKit.dll+0x1029A0  возврат из DestroyWindow при закрытии WebView
... htmlui / help / helpui ...
```

Стек восстановлен `StackWalk64` по x64 unwind-таблицам совпадающих бинарных
модулей; имя `AXObjectCache::rootObject` подтверждено экспортом установленной
WebKit.dll. `Document::axObjectCache()` может вернуть null, когда у документа
уже отсутствует render view. Вызывающий код не проверяет результат перед
`rootObject()`. Windows может синхронно запросить доступный объект в обработке
события уничтожения окна, пока `DestroyWindow` ещё не завершён.

Открытый код [WebView::onGetObject и маршрутизация WM_GETOBJECT](https://chromium.googlesource.com/external/Webkit/+/b4170928e42cb313b7c8304a796879ddb2ff7f12/Source/WebKit/win/WebView.cpp)
и [WebFrame::accessible](https://chromium.googlesource.com/external/Webkit/+/b4170928e42cb313b7c8304a796879ddb2ff7f12/Source/WebKit/win/WebFrame.cpp)
помогают сопоставить цепочку; это историческая upstream-ревизия, а не исходники
точной поставки 1С. Вывод о сбое основан на локальных дампах и бинарном коде.

## Воспроизведение

Обычный сценарий Enter в отдельной пустой базе не дал естественного сбоя
ни на исходных DLL релиза с раскраской, ни без движка. Частый MSAA-опрос и
подписка UI Automation на события также сами по себе не воспроизвели падение.

Для точного воспроизведения диагностическая DLL подписывается на
`EVENT_OBJECT_DESTROY` **только отдельного тестового процесса** и из callback
посылает `WM_GETOBJECT / OBJID_CLIENT` окну `WebViewWindowClass`. Это искусственный
стимул, воспроизводящий обнаруженный в дампе повторный вход; диагностическая
DLL не входит в поставку приложения.

- Исходные DLL релиза 0.4.0, One Dark Pro, значки и оба шрифта: падение
  `0xC0000005`, `WebKit.dll+0x260A5A`, `this == nullptr`.
- Процесс без ThemeProbe, FontProbe и UiFontEngine: тот же адрес и исключение
  при том же диагностическом стимуле.
- Исправленный движок с раскраской и обоими шрифтами: запрос в callback
  уничтожения возвращает 0, процесс штатно завершается, дампа нет. Проверено
  в отдельных процессах для знакового и нулевого расширения object ID.

Это подтверждает опасный путь в WebKit. Влияние раскраски на частоту возникновения
этого пути в рабочем ERP не измерено и не исключено. Полный естественный сценарий
пользователя в ERP остаётся отдельной приёмочной проверкой.

## Изменение движка

Раскраска СП сохранена. Добавлен один перехват импорта `USER32!DestroyWindow`
в проверенном модуле WebKit.dll. Для окна класса `WebViewWindowClass`,
принадлежащего текущему процессу и текущему потоку, он устанавливает временный
обработчик через `SetWindowSubclass` перед вызовом исходного API.

Только на время этого вызова `WM_GETOBJECT` с `OBJID_CLIENT` получает ответ 0.
Прочие сообщения и обычные запросы доступности работающей страницы проходят
по прежней цепочке. Сравниваются младшие 32 бита object ID: в реальных x64
сообщениях встречается и знаковое, и нулевое расширение `-4` до LPARAM.

При неудачном `DestroyWindow` снимается только наш временный обработчик;
результат и `GetLastError` исходного API сохраняются. Чужие окна и попытки
уничтожения окна другого потока передаются исходному API без изменения.
Рекурсивное уничтожение того же окна не снимает защиту внешнего вызова.

Исполняемый код платформенных DLL не модифицируется. Новое вмешательство —
одна IAT-ячейка WebKit и временный обработчик окна на его UI-потоке.

Snapshot содержит `browser_lifetime_guard`, `browser_destroy_calls`,
`browser_blocked_requests`, `browser_guard_failures`. Основной набор перехватов
с WebKit теперь равен 23, с доступными значками — 26. Rust проверяет подтверждение
защиты для нового набора; ABI протокола v3 не меняется.

## Проверки

- Собственный оконный fixture: доступность до уничтожения, опасный запрос внутри
  уничтожения, оба представления `OBJID_CLIENT`, чужой класс окна, неудачный
  `DestroyWindow`, сохранение ошибки и удаление временного обработчика.
- Production IAT с установленным Cairo: опасный путь до подключения и после
  остановки, защита во всех темах и диагностическом режиме; прежние проверки
  цветов WebKit, выделения, растровых элементов, шрифтов и состояния Cairo.
- Наличие импорта `USER32!DestroyWindow` проверено в установленных WebKit.dll
  8.3.26.1656, 8.3.27.2325, 8.5.1.1529 и 8.5.4.1878. Это проверка импорта,
  а не полная живая приёмка на каждой версии платформы.

Сценарий `ПланОбмена → Enter → Enter` также пройден с исправленным движком,
One Dark Pro, новыми значками и обоими шрифтами. Локальные дампы, стеки,
диагностические программы и их журналы сохранены в игнорируемых каталогах;
в поставку входит только защита и собственные regression fixtures.
