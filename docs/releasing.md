# Выпуск

Сборка релизных файлов выполняется GitHub Actions, локально выполняются проверки
разработки. Рабочие процессы: `checks.yml` для PR/ветки main, `release.yml` для
тегов. Общие команды запускает `scripts/build.py`; C++ собирает CMake/Ninja.

## Перед выпуском

- Проверьте, что проверки выбранного коммита в GitHub Actions завершились успешно.
- Выполните ручную приёмку приложения и оформления конфигуратора.
- Обновите CHANGELOG и документацию, если изменились возможности или требования.
- При изменении зависимостей проверьте их лицензии и уведомления авторов.
- Для предварительной проверки поставки используйте тег RC.

## Тег

1. Обновите версию в обоих Cargo.toml, обоих workspace-пакетах Cargo.lock,
   ui/package.json, ui/package-lock.json (верхний уровень и корневой пакет),
   ui/src-tauri/tauri.conf.json и резервную подпись версии в ui/src/App.svelte.
2. При добавлении новых зависимостей проверьте совместимость их лицензий.
   Уведомления из lock-файлов будут сформированы автоматически при сборке.
3. Оформите в CHANGELOG раздел с номером версии и датой выпуска. Если изменения
   собраны в `Unreleased`, перенесите их в этот раздел.
   Для RC укажите суффикс `-rc.N`; дату ставьте по фактическому выпуску.
   Выполните `python scripts/release_checks.py`, проверьте release notes и
   зафиксируйте изменения в Git.
4. Создайте и отправьте тег `vMAJOR.MINOR.PATCH` или `vMAJOR.MINOR.PATCH-rc.N`,
   где N начинается с 1. Тег должен указывать на проверенный коммит.

Версии манифестов/lock-файлов и тег обязаны совпадать. Другие prerelease-суффиксы
и номера с ведущими нулями не принимаются. Отправка тега означает разрешение
опубликовать соответствующий релиз после успешных проверок.

## Что выполняет CI

- Проверки общего ядра на Windows/Linux/macOS, x64/ARM64; полная проверка
  desktop/native на Windows x64 MSVC. См. [матрицу](portability.md).
- Rust 1.97.1, Node 24.13.0, Python 3.14.5, CMake 4.4.4 и Ninja 1.13.2.
  Actions закреплены полными commit SHA. Zig не требуется.
- Собирает native DLL и собственные mock fixtures. Проверяет протокол, UI,
  Rust tests/Clippy/formatting, версии и защитные проверки выпуска.
- Для тегов scripts/build.py release дополнительно собирает оба EXE с встроенным frontend и статическим
  MSVC CRT. Native DLL встраивается в EXE, loader WebView2 линкуется статически.
- Проверяет архитектуру и обычные/delay imports обоих EXE и native DLL.
  Внешний WebView2Loader.dll, VC runtime или MinGW DLL останавливают выпуск.
- Проверяет копию CLI в каталоге с пробелами, каталог тем, сохранение настроек
  и наблюдение с выключенным автоматическим применением.
- Формирует полные notices и SHA-256, передаёт файлы в отдельный job публикации.
  Только этот job получает `contents: write`; код PR не получает такой токен.

Артефакты релиза: `v8-chroma.exe`, `v8-chroma-cli.exe`, `LICENSE`,
`THIRD-PARTY-NOTICES.txt`, `SHA256SUMS.txt`. Архив для работы не нужен.
GitHub может автоматически показывать архив исходников; он не является
дистрибутивом приложения. RC публикуется как prerelease без отметки Latest,
стабильный выпуск — как Latest. Повторный выпуск существующего тега не
перезаписывает уже опубликованные файлы.

## Ручная приёмка

Проверяйте EXE из релизной сборки на чистой Windows с WebView2 Runtime:

- Запуск GUI и CLI без соседних DLL, в том числе из пути с пробелами.
- Переключение темы, сохранение настроек и повторный запуск приложения.
- Сворачивание в трей, восстановление окна и полный выход.
- Включение и отключение автозапуска.

С установленной 1С проверьте подключение к открытым и новым конфигураторам,
смену тем на лету и возврат стандартного оформления. Для светлой и тёмной тем
проверьте модули, выделение кода, меню и кнопки при наведении,
«Сервис → Параметры», сравнение-объединение.

В hosted CI нет платформы 1С. Проверка imports и mock-тесты дополняют ручную
приёмку; платформенные DLL в репозиторий не добавляются.

Релизные EXE не подписываются Authenticode. Контрольные суммы сопровождают
артефакты; полная побитовая воспроизводимость сборки не гарантируется.
